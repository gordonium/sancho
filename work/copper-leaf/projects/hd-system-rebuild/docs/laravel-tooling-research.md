# Laravel tooling and release calendars (read 2026-10-01)

Two research agents, one per topic. Unlike the hosting research these claims were **not** re-checked by a second reader; each row carries its own confidence and page. Recommendations are the agents'; the decisions are in `laravel-kit-spec.md`.

## Tooling: summary

Conclusion: a Laravel 13 kit can match the WordPress kit almost entirely with first-party or de-facto-standard tools, all confirmed current on 2026-10-01. Unconfirmed items are listed in open_questions.

Baseline facts (for the update schedule)
- Laravel 13 was released March 17th, 2026; latest tag v13.34.0 (2026-09-29). Bug fixes until Q3 2027, security fixes until March 17th, 2028. Majors are yearly (~Q1); minor and patch releases can be weekly. https://laravel.com/docs/13.x/releases
- Laravel 13 requires PHP >= 8.3. PHP 8.4 has active support until 31 Dec 2026 and security support until 31 Dec 2028. https://www.php.net/supported-versions.php
- Laravel's own docs and Forge now default to PHP 8.5, so 8.4 vs 8.5 is worth deciding now.

Mechanical gate (run before any reviewer)
- `./vendor/bin/pint --test`
- `./vendor/bin/phpstan analyse` (Larastan 3.12.2 on PHPStan 2.2.16)
- `php artisan test` (Pest 5.2.1 or PHPUnit)
- `composer audit --locked` (Composer 2.10.3)
- Each returns exit 0 on pass and non-zero on fail; the docs confirm this for Pint, PHPStan and composer audit.
- `laravel/pao` v1.1.5 ships in the Laravel 13 skeleton and turns PHPUnit, Pest, PHPStan and Rector output into compact JSON when it detects Claude Code.

Agent support
- Laravel Boost v2.10.1 (released 2026-10-01) is first-party. It installs an MCP server (`php artisan boost:mcp`), versioned guidelines, skills and committed project rules in `.ai/rules`.
- Boost regenerates CLAUDE.md, so the kit's own rules belong in `.ai/guidelines/*` or Boost will overwrite them.
- Laravel also publishes an official Claude Code plugin marketplace (`laravel/agent-skills`) and a Nightwatch MCP server that can write issue status and comments.

Deploy
- Forge is the closest fit to the WP kit's SSH-staging model: zero-downtime releases are on by default for new sites, 4 releases are retained, and there is a CLI (`forge deploy`, `forge deploy:logs`, `forge site:logs`).
- Guard-hook implication: Forge push-to-deploy is enabled by default for new sites, so a `git push` to the deploy branch is a production deploy. The hook must also cover `forge deploy`, `forge command`, `forge env:push`, `forge tinker` and `forge ssh` against production, plus `migrate:fresh`, `migrate:refresh`, `migrate:reset` and `db:wipe`.
- Code rollback does not roll back the database; migrations need their own plan.

Hosting (Gordon's question)
- Cloudflare edge is not a sound home for this app. Cloudflare Workers officially supports JavaScript, TypeScript, Python and Rust, not PHP.
- "Workers PHP" exists but describes itself as a community project not affiliated with Cloudflare or Laravel, and it forces the database onto D1.
- Cloudflare Containers is GA and runs container images on the Workers Paid plan; whether its disk persists is unconfirmed.
- The hosting-shop task is needed. The two first-party candidates are Forge plus a VPS (from $12/mo plus the server) and Laravel Cloud (from $5/mo plus usage).
- Laravel Cloud's filesystem is ephemeral, so a SQLite file cannot live there. Pulse also needs MySQL, MariaDB or PostgreSQL.

Review chain
- I propose five dimensions: the WP kit's three (backward compatibility and data safety, security, performance) plus tests and integration isolation, and deploy, environment and rollback readiness.

Caveats on sources
- https://laravel.com/for/agents and the Forge docs headers contain text addressed to AI agents. I read them as data and did not act on them; the kit should do the same.
- Zero-downtime migration practice (expand/contract) has no official Laravel page; it is community guidance only.

- **Framework baseline and support window (input to the update schedule): Laravel framework 13.x** (use; v13.34.0 (2026-09-29); 12.x line at v12.69.3; Laravel (first-party); cost: Free, open source; confirmed at primary source) Release March 17th, 2026; PHP 8.3 - 8.5; bug fixes until Q3 2027; security fixes until March 17th, 2028. Laravel 12: bug fixes ended August 13th, 2026, security until February 24th, 2027. Majors yearly (~Q1); minor/patch 'as often as every week' and 'should never contain breaking changes'. Use constraint ^13.0. *Run:* `php artisan about` (or `php artisan about --only=environment`) prints versions, drivers and environment; `composer show laravel/framework` for the installed version. Pass: version inside the supported window. Fail: past the security-fix date. *Why:* Sets the calendar: weekly patch intake, one major per year, hard deadline March 17th, 2028 for leaving 13. <https://laravel.com/docs/13.x/releases>
- **Runtime support window (input to the update schedule): PHP 8.4 (and 8.5)** (use; 8.4 branch: released 21 Nov 2024; active support until 31 Dec 2026; security support until 31 Dec 2028. 8.5: released 20 Nov 2025; active until 31 Dec 2027; security until 31 Dec 2029; PHP Group; cost: Free; confirmed at primary source) Laravel 13 requires PHP >= 8.3. Pest 5 requires PHP 8.4+. Laravel's installer docs use php.new/install/.../8.5 and Forge made PHP 8.5 the default for new servers (changelog May 31, 2026). *Run:* `php -v`. Pass: matches the version pinned in composer.json `require.php` and on the server. Fail: mismatch between local, CI and server. *Why:* 8.4 is valid but leaves active support in three months; decide 8.4 vs 8.5 at project start so local, CI, staging and production agree. <https://www.php.net/supported-versions.php>

Presets: laravel, per, psr12, symfony, empty. Config in pint.json. Optional Blade formatting (`--blade`, needs Node/Prettier). *Run:* Check only: `./vendor/bin/pint --test` -> 'will return a non-zero exit code if any code style errors are found'; exit 0 = pass. Fix only changed files: `./vendor/bin/pint --dirty` (uncommitted) or `./vendor/bin/pint --diff=main`. `./vendor/bin/pint --repair` fixes and still exits non-zero if anything was fixed. *Why:* First-party, already in the skeleton, and has a non-mutating check mode suitable for a gate. <https://laravel.com/docs/13.x/pint>
- **Static analysis: Larastan (on PHPStan)** (use; Larastan v3.12.2 (2026-09-19); PHPStan 2.2.16 (2026-09-25); Larastan community maintainers; PHPStan by Ondrej Mirtes; cost: Free (PHPStan Pro optional, not needed); confirmed at primary source) Laravel-aware PHPStan. Install: `composer require --dev "larastan/larastan:^3.0"`. Requires PHP 8.2+, Laravel 11.15+. phpstan.neon includes `vendor/larastan/larastan/extension.neon`. Levels 0-10 are cumulative; default is 0; level 5 = argument types, 6 = missing typehints, 8 = nullable access, 9-10 = strict mixed. Larastan's README example uses `level: 5`. Baseline: `--generate-baseline` writes phpstan-baseline.neon. *Run:* `./vendor/bin/phpstan analyse --memory-limit=2G --no-progress` (add `--error-format=json` for machine output; formats: table, raw, checkstyle, json, prettyJson, junit, github, gitlab, teamcity). Pass: 'Exit code 0 means there are no errors'. Fail: non-zero with the error list. *Why:* Level judgement (mine, not from a source): a greenfield app can start at level 6 with an empty baseline and ratchet to 8; never grow the baseline to make a change pass. Level 5 is the floor Larastan itself documents. <https://github.com/larastan/larastan>
- **Tests (unit and feature): Pest (on PHPUnit)** (use; Pest v5.2.1 (2026-09-17), requires PHP 8.4+ and PHPUnit 13. PHPUnit 13.3.6 and 12.5.37 (both 2026-09-29).; Pest: Nuno Maduro and team (Laravel staff); PHPUnit: Sebastian Bergmann; cost: Free; confirmed at primary source) Laravel docs: 'support for testing with Pest and PHPUnit is included out of the box'. phpunit.xml sets the `testing` environment; session and cache use the `array` driver; `.env.testing` is used if present. - **Architecture tests: Pest arch testing (arch() and presets)** (use; Part of Pest 5.x; Pest team; cost: Free; confirmed at primary source) Rules as tests. `arch()->expect('App')->toUseStrictTypes()->not->toUse(['die','dd','dump']);`. ## Proposed review dimensions

### 0. Mechanical gate (not a reviewer; must be green before any reviewer starts)

- `./vendor/bin/pint --test` exits 0 (non-zero means style errors).
- `./vendor/bin/phpstan analyse --memory-limit=2G --no-progress` exits 0 at the project's level; phpstan-baseline.neon has not grown in this change.
- `php artisan test` (or `./vendor/bin/pest`) all green, including arch tests; optional `--coverage --min=N`.
- `composer audit --locked` exits 0 (1 means an advisory, abandoned package or malware flag).
- `php artisan migrate --pretend` output captured for the reviewers if the change contains migrations.
- Results are judged by exit code, because laravel/pao changes the agent-visible output to JSON.

### 1. Backward compatibility and data safety

- Every migration has a real `down()` that reverses `up()` ('the down method should reverse the operations performed by the up method'); `php artisan migrate:rollback --pretend` on staging shows sane SQL.
- No data-losing operation without a backup and Gordon's explicit approval: `dropColumn`, `drop`/`dropIfExists`, type narrowing, shortening a string length, removing an enum value, making a nullable column NOT NULL without a backfill.
- Any `->change()` restates every modifier to keep: 'any missing attribute will be dropped' (unsigned, default, nullable, comment).
- Enum and column-type changes: all existing rows hold values valid under the new definition; proven with a query on staging data (and, given the legacy data back to the early 1990s, on a copy of the real data).
- Zero-downtime compatibility: the migration runs before the new release is activated, so the old code must still work against the new schema. New columns are nullable or have defaults; renames and drops are split across releases as expand, backfill, contract (community practice, no official Laravel page).
- Large backfills are batched (`chunk`, `lazy`) or queued, not one UPDATE inside the migration; deployments on Forge time out at 10 minutes.
- `migrate --step` used on deploy so a single migration can be rolled back; multi-server deploys use `--isolated`.
- Queued jobs that outlive the deploy: no renamed or removed job class, no changed constructor signature or property type while jobs of the old shape may still be queued or delayed; models referenced by queued jobs may be deleted (handle with `#[DeleteWhenMissingModels]` or expect ModelNotFoundException); workers are restarted in the deploy (`php artisan queue:restart` or Forge `$RESTART_QUEUES()`, or `php artisan reload`) because 'queue workers are long-lived processes' and 'will not notice changes in your code base'.
- Jobs dispatched inside transactions use `afterCommit()` or the connection's `after_commit` setting.
- Cache and session compatibility: changed cached value shapes or keys are versioned or flushed; Laravel 13 defaults (`serializable_classes` false in cache config, session `serialization` json) are respected, and changing session serialization logs every user out.
- Changing `APP_KEY` invalidates sessions and encrypted data unless the old key is listed in `APP_PREVIOUS_KEYS`.
- Public contracts unchanged or versioned: route names and URLs, API response shapes, signed URL formats already emailed to users, webhook payloads, config keys and env variable names (new required env variables are added to `.env.example` and to staging and production before the deploy).
- No `env()` calls outside `config/` (returns null once config is cached).
- Soft-deleted and legacy rows: new non-null assumptions, new unique indexes and new foreign keys are checked against existing data, including rows with missing or malformed historical values.

### 2. Security

- Mass assignment: every model touched declares `#[Fillable]`/`$fillable` (or a narrow guarded list); no `#[Unguarded]`, `Model::unguard()` or `forceFill()` with request data; controllers pass `$request->validated()` or `$request->safe()->only([...])`, never `$request->all()`. Docs example of the risk: a user sending `is_admin`.
- Authorization: every new or changed route, controller action, Livewire action and job entry point enforces a policy or gate (`Gate::authorize`, `->can()`, `can:` middleware, `#[Authorize]`, or FormRequest `authorize()`); hiding a button with `@can` is not enforcement; record lookups are scoped to the current user or tenant (no IDOR); guests are denied by default.
- Validation: every input is validated in a Form Request or `validate()`; sort and filter column names are allow-listed (`in:...`); user input never builds validation rule strings or column names.
- Raw SQL: any `DB::raw`, `whereRaw`, `selectRaw`, `orderByRaw`, `DB::statement` uses bindings; `DB::unprepared` never contains user-controlled values ('Laravel cannot guarantee that any query using raw expressions is protected against SQL injection').
- CSRF: state-changing routes sit in the `web` group under `PreventRequestForgery`; every `preventRequestForgery(except: [...])` entry is justified and has its own authentication.
- Webhooks: every CSRF-excluded inbound endpoint verifies a signature with a constant-time comparison, rejects replays, and has a test for a bad signature.
- Signed URLs: public links that act on data use `URL::signedRoute` / `temporarySignedRoute` and the `signed` middleware; `hasValidSignatureWhileIgnoring` lists are minimal.
- Output: Blade uses `{{ }}`; every `{!! !!}` is on trusted or sanitised content; no user input in `redirect()` targets without an allow-list.
- File uploads: validated with `File::types([...])->max(...)` or `mimes` plus size (extensions alone are not enough); stored with `store()` / `hashName()`, never `getClientOriginalName()` ('considered unsafe'); stored outside the public disk unless meant to be public; SVG only with explicit intent (`image:allow_svg`).
- Secrets: nothing secret in the repository, logs, exception messages or front-end bundles; `.env` not committed; new secrets exist per environment; staging uses sandbox credentials.
- Production configuration: `APP_DEBUG=false` ('you risk exposing sensitive configuration values'), `APP_ENV=production`, web root is `public/`, Telescope and Pulse dashboards gated (`viewPulse`), session cookie flags secure, http_only and same_site set.
- Rate limiting on login, password reset, public forms and any endpoint that sends mail or calls a paid API (`throttle` middleware or `RateLimiter`).
- No `unserialize`, `eval`, `extract` or shell execution on user input; queued jobs carrying sensitive data implement `ShouldBeEncrypted`.
- Dependencies: `composer audit --locked` clean; any new package is maintained (recent release) and its advisories checked; no open Dependabot alerts.
- Agent-specific: no production credentials in the local `.env` (Boost's Database Query tool uses the local connection); Nightwatch MCP used read-only unless approved.

### 3. Performance

- N+1: `Model::preventLazyLoading(! $this->app->isProduction())` is enabled in AppServiceProvider so tests and staging throw `LazyLoadingViolationException`; relations used in loops, Blade views and API resources are eager loaded (`with`, `load`, `withCount` instead of loading a relation to count it).
- `Model::preventSilentlyDiscardingAttributes(! $this->app->isProduction())` is on, so fill mistakes surface in tests.
- Query count and time for each changed page or endpoint measured on staging with realistic data volume (the legacy dataset): `DB::listen` logging, `DB::whenQueryingForLongerThan(500, ...)`, Pulse slow-query card or Nightwatch; compared before and after the change.
- Large result sets use pagination, `chunk`, `lazy` or `cursor`; no `Model::all()` or unbounded `get()` on legacy-sized tables.
- New `where`, `orderBy`, join and foreign-key columns have indexes; `EXPLAIN` checked for new heavy queries; index creation on large tables is planned for lock time.
- Slow or external work (mail, HTTP calls, PDF and image processing, imports, exports) is queued, with `#[Tries]`, `#[Timeout]`, `#[Backoff]` set and the job timeout shorter than the connection's `retry_after`.
- Outbound HTTP calls have timeouts and retries configured and are not made inside loops or database transactions.
- Caching: expensive reads are cached with an explicit TTL and an invalidation path; no cache key collisions between staging and production (prefixes).
- Deploy optimisation is in the deploy script: `php artisan optimize` (config, events, routes, views), and long-running services reloaded (`php artisan reload` or queue/Horizon/Pulse restart); `composer install --no-dev --optimize-autoloader` is my recommendation, not quoted from a fetched page.
- Route cache compatibility: the change does not break `route:cache`; `php artisan optimize` succeeds on staging.
- Front-end: assets built with `npm run build`, no dev server references, no unbounded Livewire polling.
- SQLite specifics if SQLite is the engine: write concurrency and long-running imports are considered; Pulse cannot store in SQLite.

### 4. Tests and integration isolation

- Every behaviour changed has a feature test that fails without the change (Laravel docs: 'most of your tests should be feature tests').
- `Http::preventStrayRequests()` is active in the base test case; every external call is faked with `Http::fake([...])` and asserted with `Http::assertSent`.
- Mail and notifications use `Mail::fake()` / `Notification::fake()` with `assertSent` or `assertQueued`; nothing is delivered from tests; staging uses `Mail::alwaysTo(...)`, the `log` driver or a mail trap.
- Queued work uses `Queue::fake()` or `Bus::fake()` to assert dispatch, plus at least one test that runs the job's `handle()` for real.
- Authorization has negative tests: wrong user, guest, and wrong tenant get 403 or 404.
- Validation has negative tests for each rule that protects data integrity.
- Migrations are exercised by the suite (`RefreshDatabase`) on the same database engine as production where behaviour differs (SQLite vs MySQL/Postgres).
- Arch tests cover the kit's structural rules (no `dd`/`dump`/`die`, no `env()` outside config, strict types if adopted).
- Tests run against the `testing` environment only (phpunit.xml / `.env.testing`); no test reads staging or production credentials; `NIGHTWATCH_ENABLED=false` in phpunit.xml.
- A browser smoke test (`visit(...)->assertNoSmoke()`) exists for each changed page when the change touches UI.
- No test was deleted, skipped or weakened to get green; coverage threshold (if set) still met.

### 5. Deploy, environment and rollback readiness

- The change was deployed to staging by the normal route (Forge staging site or equivalent), not hand-copied; `forge deploy:logs` shows success and `/up` returns 200.
- Staging and production are distinct sites with distinct databases, `.env` files, APP_KEYs, queues, cache prefixes, mail settings and third-party credentials; `php artisan about --only=environment` confirms each.
- Production deploy trigger is controlled: push-to-deploy is off for production or the production branch is protected; the agent has no production Forge token, SSH key or database credentials.
- Deploy script reviewed if changed: order is create release, composer install, build assets, `php artisan migrate --force`, `php artisan optimize`, activate release, restart queues; no `migrate:fresh`, `optimize:clear` in production, or `--seed`.
- A backup was taken and verified immediately before any ship that includes a migration (`php artisan backup:run --only-db`, archive present on the remote disk).
- Rollback path written down for this specific ship: which release to reactivate, which migrations to roll back and whether that loses data, which env or config changes to revert, and how queued jobs created by the new code behave under the old code.
- Version, changelog or release notes entry and git tag prepared; the tag points at the commit that passed the gate and the reviews.
- New env variables, scheduled tasks, queue workers, daemons and cron entries are documented and present on staging and production.

2. ## Stated policies

- **Laravel framework**: Semantic Versioning. 'Major framework releases are released every year (~Q1), while minor and patch releases may be released as often as every week.' Minor and patch releases should never contain breaking changes. Bug fixes for 18 months, security fixes for 2 years, for all releases. Use a constraint such as ^13.0. Named arguments are not covered by the backwards-compatibility guarantee. <https://laravel.com/docs/releases>
- **Laravel first-party packages (Pint, Boost, Tinker, Sanctum, etc.)**: Follow semver; 'For all additional libraries, only the latest major release receives bug fixes.' They do not necessarily bump majors with the framework (Pint is still 1.x), but a framework upgrade can require a package major (Laravel 13 guide: laravel/boost ^2.0, laravel/tinker ^3.0, phpunit ^12.0, pest ^4.0). <https://laravel.com/docs/13.x/upgrade>
- **Laravel security reporting**: Report privately by email to Taylor Otwell; supported versions are those in the docs support policy; advisories are published on the laravel/framework repository's Security Advisories tab (three in 2026 so far: 2026-06-01 High, 2026-06-08 Moderate, 2026-09-10 Low). <https://github.com/laravel/framework/security/policy>
- **Laravel supported databases**: First-party support: MariaDB 10.3+, MySQL 5.7+, PostgreSQL 10.0+, SQLite 3.26.0+, SQL Server 2017+. These are minimums the framework accepts, not vendor support windows. <https://laravel.com/docs/13.x/database>
- **PHP**: Yearly feature release (GA in late November). Each branch: 2 years active support (bugs + security), then 2 years critical security fixes only; support ends 31 December of the fourth year after GA. 4 years total. <https://www.php.net/supported-versions.php>
- **PHP release process (policy text)**: Yearly release cycle, 4-year life cycle: 2 years bug fixes, 2 years security fixes only, ending Dec 31 24:00 UTC. <https://github.com/php/policies/blob/main/release-process.rst>
- **Ubuntu**: LTS released every two years (April of even years), 5 years of standard security maintenance; +5 years ESM with Ubuntu Pro; optional Legacy add-on beyond. Interim releases every 6 months get only 9 months of updates and are not for production. <https://ubuntu.com/about/release-cycle>
- **Node.js**: Majors are Current for 6 months. Through Node 26: even-numbered releases become Active LTS, odd ones die after 6 months. From Node 27: annual cycle, every major becomes LTS after its Current phase, preceded by a 6-month Alpha. LTS gets critical fixes for 30 months total. Production should use Active LTS or Maintenance LTS only. <https://nodejs.org/en/about/previous-releases>
- **Vite**: No fixed release cycle; patches weekly as needed, majors roughly yearly and 'generally align with Node.js EOL schedule'. Regular patches for the current minor; important + security fixes for the previous major and previous minor; security-only for the second-to-last. Targets Node LTS versions. <https://vite.dev/releases>
- **PostgreSQL**: One major per year; each major supported 5 years from release, then a final minor and EOL. Minors at least once every three months, low-risk (stop, install binaries, restart). Major upgrades need dump/reload or pg_upgrade. <https://www.postgresql.org/support/versioning/>
- **MySQL**: Two tracks. LTS (8.4.x, 9.7.x): 5 years premier + 3 years extended, no feature removals inside the series. Innovation releases: supported only until the next Innovation release, behaviour may change. Upgrades go LTS to the next LTS (8.4 -> 9.7); an LTS series cannot be skipped. Use LTS only. <https://dev.mysql.com/doc/refman/8.4/en/mysql-releases.html>
- **SQLite**: Intent to support through 2050; C API and on-disk format kept fully backwards compatible; database files are bit-identical across platforms. No scheduled major upgrades to plan for; the version follows the OS/PHP build. <https://www.sqlite.org/lts.html>
- **Composer version constraints**: Caret ^1.2.3 means >=1.2.3 <2.0.0 (minor and patch allowed, major blocked); for 0.x the caret locks the minor (^0.3 means >=0.3.0 <0.4.0). Tilde ~1.2.3 means >=1.2.3 <1.3.0 (patch only); ~1.2 means >=1.2 <2.0.0. So with caret constraints 'composer update' delivers patch+minor, and a major always requires editing composer.json. <https://getcomposer.org/doc/articles/versions.md>
- **composer outdated**: Lists installed packages with newer versions. Red (!) = semver-compatible update available, should upgrade; yellow (~) = newer version with possible BC breaks (a major). Flags: --direct (-D), --major-only (-M), --minor-only (-m), --patch-only (-p), --strict (non-zero exit if anything outdated), --format=json, --no-dev, --locked. Related: 'composer update --patch-only', '--minimal-changes', '-W'; 'composer bump' raises lower bounds to installed versions. <https://getcomposer.org/doc/03-cli.md>
- **composer audit and blocking**: 'composer audit' checks installed (or --locked) packages against security advisories from the Packagist.org API; exit 0 = clean, 1 = issues; --format=json/table/plain/summary; --no-dev; --abandoned=ignore/report/fail (default fail since 2.7). Audit also runs automatically after install/require/update/create-project unless --no-audit. Since 2.9, versions with advisories are blocked during update/require by default (audit.block-insecure true). Since 2.10 this lives under config.policy: advisories (block true, audit fail, ignore-id with reasons), abandoned, malware (block true), and cooldown.period (e.g. '7 days') to withhold freshly released versions. The old config.audit keys are deprecated. <https://getcomposer.org/doc/06-config.md>
- **Pest**: Semver. 'Bug fixes will be available for outdated versions for a duration of 12 months following the latest version's release.' Each major raises the PHP floor (Pest 3: 8.2, Pest 4: 8.3, Pest 5: 8.4) and tracks a PHPUnit major (Pest 5 on PHPUnit 13). Roughly one major a year, late summer; not on Laravel's cadence. <https://pestphp.com/docs/support-policy>
- **Livewire**: No published support window found (unconfirmed). v4 supports Laravel 10 through 13 and PHP ^8.1; v3 to v4 upgrade guide says most apps upgrade with minimal changes and points to Laravel Shift. Own cadence. <https://livewire.laravel.com/docs/upgrading>
- **Larastan**: No dated support policy. Compatibility table: 1.x for Laravel < 9, 2.x for 9.0 to 11.15, 3.0+ for 11.16+; PHP 8.2+. Majors follow PHPStan majors, not Laravel's. <https://github.com/larastan/larastan>
- **DomPDF**: 'only the latest release of Dompdf is actively supported.' Security issues reported privately via GitHub Security Advisories. <https://github.com/dompdf/dompdf/security/policy>
- **Google API PHP client**: Officially supported by Google but 'considered complete and are in maintenance mode': critical bugs and security issues only. The google/apiclient-services dependency is 0.x; the README tells users to pin it before production. Unused services can be removed with Google\Task\Composer::cleanup. <https://github.com/googleapis/google-api-php-client>

## Advisory feeds

- **Packagist security advisories API (what composer audit reads)**: Run 'composer audit --locked --format=json' in CI and on a schedule; exit code 1 means an advisory or abandoned package matched. Direct API: GET https://packagist.org/api/security-advisories/?packages[]=vendor/package (or ?updatedSince=<timestamp>); each advisory carries advisoryId, affectedVersions, cve, severity and sources (GitHub and/or FriendsOfPHP/security-advisories). <https://packagist.org/apidoc>
- **FriendsOfPHP/security-advisories**: A public-domain (Unlicense) database of PHP advisories; its README says it is not authoritative and directs users to run 'composer audit' from the project root. It is one of the sources feeding both Packagist and the GitHub Advisory Database, so it does not need a separate check. <https://github.com/FriendsOfPHP/security-advisories>
- **GitHub Advisory Database (Composer ecosystem, registry packagist.org)**: Enable the dependency graph, Dependabot alerts and Dependabot security updates on each repo (Settings > Advanced Security). Alerts fire only for GitHub-reviewed advisories; a security-update PR is raised to the minimum patched version. Sources include GitHub-reported advisories, NVD and the FriendsOfPHP database. <https://docs.github.com/en/code-security/security-advisories/working-with-global-security-advisories-from-the-github-advisory-database/about-the-github-advisory-database>
- **laravel/framework Security Advisories tab**: Watch the repository for security advisories (GitHub 'Watch > Custom > Security alerts'), or have the agent fetch the advisories page in the weekly run. These also flow into the GitHub Advisory Database and therefore into composer audit and Dependabot. <https://github.com/laravel/framework/security/advisories>
- **Composer's built-in blocking (policy.advisories.block / audit.block-insecure)**: Nothing to run: Composer 2.9+ refuses to resolve to a version with a known advisory during update/require, and 2.10+ blocks malware-flagged versions at install. Keep Composer itself current ('composer self-update') and never set policy to false. Any ignore must be a named advisory ID with a reason in composer.json (policy.advisories.ignore-id). <https://getcomposer.org/doc/06-config.md>
- **Roave/SecurityAdvisories (optional belt-and-braces)**: 'composer require --dev roave/security-advisories:dev-latest' adds a conflict list rebuilt hourly from FriendsOfPHP and GitHub advisories; it blocks vulnerable versions at require/update time, not at 'composer install' from a lock file. Largely redundant with Composer 2.9+ blocking; note only. <https://github.com/Roave/SecurityAdvisories>
- **Support-window calendar (Laravel, PHP, Node, Ubuntu, DB end dates)**: Monthly, re-fetch the primary pages (laravel.com/docs/releases, php.net/supported-versions.php, nodejs/Release schedule.json, postgresql.org/support/versioning) and diff against the stored calendar. endoflife.date offers the same data as JSON (e.g. https://endoflife.date/api/laravel.json, /api/ubuntu.json, /api/mysql.json) for a mechanical cross-check; it is a secondary source and must not override a primary page. <https://endoflife.date/api/laravel.json>
- **npm advisories (Vite build chain)**: Dependabot alerts cover the npm ecosystem from the same GitHub Advisory Database; 'npm audit' in CI is the usual local check (npm audit behaviour was not fetched in this run: unconfirmed). <https://docs.github.com/en/code-security/security-advisories/working-with-global-security-advisories-from-the-github-advisory-database/about-the-github-advisory-database>

## Proposed schedule (the agent's; the spec's version is in laravel-kit-spec.md section 9)

- **Every push and nightly (per app)**: CI gate: composer validate; composer install from the lock file; composer audit --locked; Pint --test; Larastan; Pest; npm ci; npm run build; npm audit. A red result blocks merge and deploy. *Rule:* On every push/PR, plus a scheduled run at a fixed hour daily so an advisory published against an untouched app still turns the build red within 24 hours. *Unattended:* Fully unattended. Owner sees only failures. *Why:* composer audit exits 1 on any advisory or abandoned package; this is the mechanical equivalent of the WordPress kit's guard hook for dependency risk. Auto-merge is only safe because this gate exists.
- **Weekly**: Dependency PRs: one grouped PR for Composer patch+minor updates, one for npm patch+minor, one for GitHub Actions. Auto-merge when (a) update type is patch for any dependency, or minor for a require-dev dependency, (b) the package is not 0.x (google/apiclient-services is 0.x: never auto-merge), (c) the release is at least 7 days old (Composer policy.cooldown.period '7 days' or Dependabot cooldown), (d) all status checks are green. Everything else waits for the monthly review. *Rule:* Every Monday (Dependabot schedule.interval weekly, day monday). Laravel itself ships minors/patches 'as often as every week', so the Laravel minor arrives through this PR. *Unattended:* Agent/bot unattended to the main branch and to staging. Production deploy stays an owner step unless the kit's guard explicitly permits auto-deploy of patch-only releases (owner decision, see open questions). *Why:* Laravel policy says minor and patch releases never contain breaking changes; Composer caret constraints already limit updates to minor+patch; branch protection with required checks is GitHub's documented precondition for auto-merge.
- **Monthly**: Review run per app: (1) merge the minor updates of production dependencies that were not auto-merged, after reading their changelogs; (2) produce the majors report with 'composer outdated --direct --major-only --format=json' and 'npm outdated'; (3) refresh composer.lock/package-lock fully ('composer update' within constraints, lock-file maintenance); (4) 'composer self-update'; (5) on self-owned servers apply OS package updates and reboot if required; apply database minor releases; (6) re-fetch the support calendar from primary sources and diff against the stored copy; (7) deploy the month's batch to production. *Rule:* First Monday of each month. Calendar diff: any date that moved, or any component now within 180 days of its security end date, raises a flag for the owner. *Unattended:* Agent prepares everything and stages it unattended behind green tests. Owner approves the production deploy and any server reboot window, and reads the majors report. *Why:* PostgreSQL ships minors at least quarterly and recommends always running the current minor; Ubuntu security maintenance arrives as package updates; a monthly calendar refresh is what catches a newly announced Laravel 14 date or a changed EOL.
- **Quarterly**: (1) Decide and execute non-framework major upgrades one at a time (Livewire, Pest, Larastan/PHPStan, DomPDF, google/apiclient, Vite, Tailwind), each on its own branch; (2) Rector dry run (--dry-run) with rector-laravel and withPhpSets to report drift; (3) review every entry in policy.advisories.ignore-id and remove or re-justify it; (4) check abandoned-package warnings; (5) restore-from-backup drill on staging; (6) kit parity review: compare the Laravel kit and the WordPress kit and cross-apply lessons from each ERRORS log. *Rule:* First Monday of January, April, July and October. A package major is taken when its previous major stops receiving bug fixes within the next two quarters (Pest rule: previous major gets 12 months after the new one ships, e.g. Pest 4 until 2027-07-28, so move to Pest 5 by the April 2027 run) or when a Laravel/PHP upgrade requires it. *Unattended:* Agent does the branch, the Rector report and the upgrade attempt unattended; a major merges only with owner approval. The restore drill and kit parity review are agent-run with an owner read. *Why:* These packages do not follow Laravel's cadence, publish short or no support windows (DomPDF: latest release only), and a stale one blocks the yearly framework upgrade because Composer cannot resolve it.
- **Yearly - Laravel major**: Upgrade every app from Laravel N to N+1. Preflight: 'composer why-not laravel/framework ^N+1' must show no blocking package (barryvdh/laravel-dompdf, Livewire, Larastan each have to declare support). Method: Laravel Boost's /upgrade-laravel-vN+1 prompt (free) or a Laravel Shift run (about $19 per app), then the official upgrade guide's high- and medium-impact items by hand, then full tests, then staging soak, then production. *Rule:* Let R = release date of Laravel N+1, B = bug-fix end of Laravel N, S = security-fix end of Laravel N. ADOPT RULE: begin when all of (a) today >= R + 30 days, (b) every direct dependency resolves against ^N+1, (c) the app's test suite is green on the upgrade branch. START no later than R + 90 days. FINISH no later than B (about R + 6 months). HARD DEADLINE S - 90 days: an app still on N after that date is escalated to the owner weekly. New projects always start on the newest major that is at least 30 days old. For 13 to 14: R is unannounced (~Q1 2027 by policy); B = Q3 2027 (treat as 2027-09-30); S = 2028-03-17, so hard deadline 2027-12-17. Pilot on the smallest app first, then roll the rest within 30 days. *Unattended:* Agent does preflight, branch, automated upgrade, guide checklist, tests and staging unattended. Owner approves the start (it is a scheduling decision across apps), reviews the diff and approves production. *Why:* Security fixes last 24 months and majors ship every 12, so N loses security support about when N+2 ships: skipping a major is not possible. Bug fixes end at 18 months, so finishing by B keeps every app inside the bug-fix window at all times. Laravel states it aims for upgrades of 'one day or less' (the 13 guide estimates 10 minutes).
- **Yearly - PHP minor**: Move each app and its server to the newest PHP minor that passes the adoption rule. Steps: add the new version to the CI matrix as soon as it is GA; set composer.json config.platform.php / require php accordingly; 'composer update --dry-run' to confirm resolution; Rector withPhpSets dry run; switch staging; switch production. *Rule:* Let G = GA date of PHP X.Y (late November; 8.6 planned 2026-11-19). ADOPT RULE: adopt when all of (a) the Laravel support table lists X.Y for the app's Laravel major, (b) all Composer dependencies resolve on X.Y, (c) CI is green on X.Y, (d) today >= G + 90 days (so roughly X.Y.3), (e) the host or OS offers X.Y. Do it in the same spring window as the Laravel major, PHP first or Laravel first but never both in one deploy. FLOOR RULE: no production app runs a PHP branch past its active-support end date (31 December, two years after GA) unless the owner signs an exception, and never within 180 days of its security end date. Today: 8.4 leaves active support 2026-12-31, so apps should be on 8.5 by then; 8.6 is evaluated from about 2027-02-19 and only if Laravel lists it. *Unattended:* Agent does CI matrix, dry runs and staging switch unattended. Owner approves the production runtime switch (it is a server or host change). *Why:* PHP gives 2 years of bug fixes then 2 of security-only; Laravel and Pest raise their PHP floors every year (Laravel 13 needs 8.3, master needs 8.4, Pest 5 needs 8.4), so lagging on PHP blocks the framework upgrade.
- **Yearly - Node and front-end build chain**: Move the build Node version to the current Active LTS; upgrade Vite/laravel-vite-plugin majors when the running Vite major drops to security-only. *Rule:* A Node line becomes LTS in late October (Node 26 on 2026-10-28). Switch in the January quarterly run (LTS date + about 60 days). FLOOR RULE: be off a Node line at least 90 days before its end date (Node 22 ends 2027-04-30, so off it by 2027-01-30; Node 24 ends 2028-04-30). Pin the version in .nvmrc and CI so it is one line to change. *Unattended:* Fully unattended behind a green 'npm ci && npm run build' and test suite; no owner step unless the app serves SSR from Node. *Why:* Node is only a build-time dependency for a Vite-built Laravel app, so the risk is low, but Vite requires a supported LTS (20.19+ or 22.12+ today) and drops EOL Node versions at its majors.
- **Every two years - server OS and database major (self-owned servers only)**: Build a fresh server on the new Ubuntu LTS and migrate, rather than upgrading in place. Take the database major that ships with it (PostgreSQL via pg_upgrade or dump/reload; MySQL one LTS series at a time, 8.0 to 8.4 to 9.7). SQLite needs nothing: it moves with the OS and the file format is stable. *Rule:* A new LTS ships in April of even years; adopt for new servers once the .1 point release is out (26.04.1 shipped 2026-08-31, so 26.04 is eligible now). FLOOR RULE: migrate off an LTS at least 12 months before its standard support ends (24.04: migrate by April 2028; 22.04: already inside the window, migrate now). Database: be off a PostgreSQL major 6 months before its final release date (16: by May 2028); never run MySQL 8.0 on a new server (upstream support ended 2026-04-21). *Unattended:* Agent can script and rehearse the build on a staging server. The cut-over, DNS and data migration are owner-approved steps. *Why:* The OS pins the default PHP, database and Node versions (24.04: PHP 8.3, MySQL 8.0, PostgreSQL 16; 26.04: PHP 8.5, MySQL 8.4, PostgreSQL 18), so the OS date is what actually limits the PHP floor rule on a self-owned box. Not applicable if the app runs on a managed platform; then the host's runtime list replaces this row.
- **On a security advisory**: Triage by severity and reachability, patch to the minimum fixed version, test, deploy. If no fixed version exists: mitigate (disable the feature, add a guard), and only then record a time-boxed ignore with the advisory ID and reason in composer.json. *Rule:* Trigger: nightly 'composer audit --locked' exits non-zero, a Dependabot alert or security-update PR opens, or a new entry appears on laravel/framework's advisories tab. Clock starts at detection. Critical or High in a production dependency: patched on staging within 24 hours, production within 48 hours. Moderate: within 7 days. Low, or dev-only dependency: next weekly batch. An advisory on a Laravel major that is past its security end date is an immediate forced upgrade. *Unattended:* Agent does detection, the patch branch, tests and staging deploy unattended and notifies the owner at once. Owner approves production deploy (pre-authorisable for patch-level fixes with green tests) and any ignore or mitigation decision. *Why:* Composer and Dependabot both resolve to the minimum patched version, which is normally a patch release and safe behind tests. DomPDF (20 advisories on record) and Laravel itself (three advisories in 2026) are the likeliest sources.
- **On an end-of-support date approaching**: Open an upgrade job for the affected app and component and put it in front of the owner. *Rule:* Computed in the monthly calendar diff: flag at 180 days, 90 days and 30 days before any security end date that an app depends on (Laravel major, PHP branch, Node line, Ubuntu LTS, PostgreSQL/MySQL major, Pest major). Next dates on today's calendar: PostgreSQL 14 on 2026-11-12; PHP 8.2 on 2026-12-31; Laravel 12 on 2027-02-24; Node 22 on 2027-04-30; Ubuntu 22.04 in spring 2027; Pest 4 on 2027-07-28. *Unattended:* Fully unattended detection and notification; the upgrade itself follows the relevant yearly row. *Why:* Must-never 10 in the house rules: never let the pipeline fall behind silently. A date rule that fires on its own replaces remembering.
- **On project creation**: Start on the newest Laravel major that is at least 30 days old, the newest PHP minor that Laravel lists and that is at least 90 days old, Active LTS Node, and current majors of Livewire, Pest, Larastan and Pint. Commit composer.lock and package-lock.json; add dependabot.yml (or renovate.json), the CI gate, branch protection with required checks, config.policy with a cooldown, and an entry for the app in the shared support calendar. *Rule:* Today that means Laravel 13.x, PHP 8.5, Node 24 (moving to 26 after 2026-10-28 plus 60 days), Pest 5, Livewire 4, Larastan 3, Pint 1, Composer 2.10. *Unattended:* Agent unattended from a template; owner confirms the stack once per project. *Why:* Every app on the same versions means one upgrade procedure rehearsed on the smallest app and replayed on the rest, which is what makes one maintainer with an agent viable across several apps.

## Upgrade tooling

- **Laravel Shift**: Hosted service that performs a Laravel major upgrade and opens a pull request with atomic commits and review comments; signs in through GitHub, GitLab or Bitbucket (a Docker option exists for local runs). Named in the official upgrade guide. Also has Livewire 3.x to 4.x, PHPUnit and Tailwind shifts. Cost: Pay as you go $9-$39 per Shift: Laravel 12.x to 13.x is $19, 11.x to 12.x $29, older hops $39; Livewire 3.x to 4.x $9; PHPUnit upgrades and Tailwind 3 to 4 free; Laravel Linter and PreShift free. Shifty Plans 'starting at $99 per year' (Workbench access, priority queue, CI tools). The plans and pricing pages returned 403, so plan contents beyond the homepage line are unconfirmed. <https://laravelshift.com/shifts>
- **Laravel Boost (first-party MCP server)**: Gives an AI agent Laravel-specific context and guided upgrade prompts. The Laravel 13 upgrade guide says: install in a Laravel 12 app and run the /upgrade-laravel-v13 slash command in Claude Code (needs laravel/boost ^2.0). This is the agent-native route for the yearly major and the natural fit for the kit. Cost: Free, MIT licence. <https://laravel.com/docs/13.x/upgrade>
- **Rector with driftingly/rector-laravel**: Automated code refactoring. 'composer require --dev driftingly/rector-laravel'; in rector.php use ->withComposerBased(laravel: true) so rules follow the Laravel version in composer.json (the older LaravelLevelSetList::UP_TO_LARAVEL_130 constants are deprecated). Extra sets: LARAVEL_CODE_QUALITY, LARAVEL_COLLECTION, LARAVEL_STATIC_TO_INJECTION, LARAVEL_FACADE_ALIASES_TO_FULL_NAMES, LARAVEL_ARRAY_STR_FUNCTION_TO_STATIC_CALL. Rector core's ->withPhpSets() reads the PHP version from composer.json for PHP-minor upgrades. Run with --dry-run in CI to report drift. Cost: Free; rector-laravel is MIT. Rector core's licence was not stated on the page fetched (unconfirmed, repository is public). <https://github.com/driftingly/rector-laravel>
- **Dependabot (GitHub)**: .github/dependabot.yml with package-ecosystem composer, npm and github-actions; schedule.interval daily/weekly/monthly/quarterly/semiannually/yearly/cron; groups (patterns, dependency-type, update-types minor/patch/major, applies-to version-updates/security-updates) to collapse updates into one PR; cooldown (default-days, semver-major-days, semver-minor-days, semver-patch-days); ignore with update-types such as version-update:semver-major; default limit of 5 open version PRs. Auto-merge: a workflow using dependabot/fetch-metadata reads update-type and runs 'gh pr merge --auto' when it equals version-update:semver-patch, with 'Require status checks to pass before merging' enabled on the branch. Security updates are separate and go to the minimum patched version. Cost: Alerts, security updates, version updates and dependency graph are listed under 'Available for all GitHub plans'. <https://docs.github.com/en/code-security/dependabot/working-with-dependabot/dependabot-options-reference>
- **Dependabot auto-merge recipe**: Official example workflow for auto-merging by update type behind required status checks. Cost: Free (GitHub Actions minutes apply). <https://docs.github.com/en/code-security/dependabot/working-with-dependabot/automating-dependabot-with-github-actions>
- **Renovate**: Alternative to Dependabot with finer control; supports Composer. packageRules with matchUpdateTypes (major, minor, patch, pin, digest...) and groupName for grouping; schedule (cron or 'before 3am on Monday'); minimumReleaseAge to hold back fresh releases; lockFileMaintenance (refresh composer.lock/package-lock on a schedule, a low-risk automerge candidate); vulnerabilityAlerts and osvVulnerabilityAlerts. Automerge: {matchUpdateTypes:[minor,patch], matchCurrentVersion:'!/^0/', automerge:true}; it will not merge until status checks pass (unless ignoreTests is set); automergeType 'branch' merges without opening a PR; platformAutomerge true by default. Caveats: can take about two hours, and mandatory reviews or CODEOWNERS block it. Cost: Renovate CLI: free, open source (AGPL-3.0-only), self-hosted. Mend Renovate Community (hosted GitHub app): free. Enterprise: paid, price not published on the page. <https://docs.renovatebot.com/key-concepts/automerge/>
- **Composer itself (composer outdated / audit / update --patch-only / bump, policy.cooldown)**: The mechanical baseline that works with no hosted service: 'composer outdated --direct --major-only --format=json' for the monthly majors report, 'composer update --patch-only' for a patch-only run, 'composer audit --locked' as a CI gate, and config.policy.cooldown.period (e.g. '7 days') so freshly published versions are not pulled in immediately. Cost: Free. <https://getcomposer.org/doc/03-cli.md>
