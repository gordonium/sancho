## The three skills (plugin-edit, plugin-review, plugin-ship)

The three skills are a fixed chain (plugin-edit -> plugin-review -> plugin-ship) that turns the kit's rules file into an ordered procedure, so every job, even a one-line fix, passes the same gates. Edit covers intake, repo preflight, staging connection behind the live-site guard, investigation, plan and approval, implementation, staging deploy and a written test matrix with log proof. Review runs three independent read-only subagents (backward compatibility, security, performance) on the diff and loops fix -> redeploy -> retest -> rerun all three until no FAIL remains. Ship bumps the version, writes owner-facing release notes, proves staging equals what is committed, commits, tags and pushes, then stops: publishing the GitHub Release (the act that reaches production) is always Gordon's, followed by read-only production checks, rollback guidance, a human-developer time estimate and cleanup. Almost every gate is enforced by instruction only; the two real mechanisms are the SiteDistrict guard hook and the deliberate absence of the gh CLI.

### Weaknesses the reader found

- CONFIRMED HOLE (by calling the guard's check functions directly on sample text): bin/sitedistrict-live-site-guard.py:232 only checks that the remote command STARTS with 'cd <staging> &&'. A command of the form 'cd <staging> && ls ; rm -rf public_html' or '... // rm -rf sites' passes Rules F-J. If the staging folder name is mistyped but still contains 'sitedistrict.com', the cd fails, the && part is skipped, and whatever follows ; or // runs in the home folder that holds every live site.
