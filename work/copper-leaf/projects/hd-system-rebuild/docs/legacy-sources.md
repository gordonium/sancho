# Legacy sources on this Mac (2026-10-01)

Gordon: "even those tables in WP are suspect ... We should dig all the way back into original MS Access database backups if we can." [gordon 2026-10-01] They are here. A search by file name found the Access files and a long run of database backups in Gordon's Sync folders. **Nothing was opened.** What follows is names, sizes and dates.

## What the names and dates suggest (unconfirmed until opened)

- **The Access booking system.** `BOOKING2/` holds `Bkgdata.mdb` (the data), `BKG46A.MDB` and `BOOKING.MDB` (most likely the program), and an `ARCH/` folder with an older `BKGDATA.MDB` and `MEMOS.MDB` from 1996. There are several copies of the folder with different dates. The data file grows over time: 8.0 MB in November 1999, 12.5 MB in October 2003, 13.5 MB in May 2005, and **15.4 MB in the newest copies, modified 2008-10-29 and 2009-02-07**. So the Access system was still being written to in late 2008. The census found one job in December 2007 and none until October 2008 [doc:census-part2-2026-10-01.md]; if the newest Access file holds 2008's jobs, that gap is a failure of the 2014 load, and the jobs are recoverable. This is the first thing to check.
- **v1 "legacy".** `HDonline/backups/phase2_backup_052709` (May 2009) and `HDONLINE backup 20120531` are from before v2. The 2009 folder contains a database file named `hdlocal10-19-08.sql`: 19 October 2008, the same month the census shows jobs resuming.
- **The move into v2, 2014.** `EXPORT 20140722/booking_new07-22-14_*.sql` and `hdonline-migration_20140729.sql`, then a local database from 2014-11-18. The census found that 8,092 of v2's jobs were created on 2014-12-10; these files are from the months just before.
- **Around the 2015 note-deletion bug.** Live backups dated 2015-01-05, 2015-02-01, 2015-04-13, 2015-07-24 and 2015-08-17, development copies from 2015-06-11, and a folder named `20150817 rebuild` containing `REPORT_DATA_NOTES` files, which by its name is the table the bug emptied. A folder named `HDONLINE DATA HUNTING 20170815` records an earlier recovery attempt.
- **v2 afterwards.** A backup "from hostgator" (2017-12-01), a set of exports dated 2019-11-02 (`hdonlinedh18*.sql`, about 220 MB), `REPORT_DATA_NOTES_20200617.sql` (149 MB), and `homedire_hdo_a2.sql` (2020-12-15), which is the database the WordPress migration read.
- **v2's source code.** `hdonline_v2grayson_master-from-github_20210629_5-years-old.zip` and `HDonlineLIVE-master DOWNLOADED FROM github 20191114 gs.zip`.
- **The 2020 to 2021 migration.** `202103 Data Migrator/hdo-migrator_contacts-moderate-reports_GTG20210315.sql`: by its name, the `CONTACTS`, `MODERATE` and `REPORTS` tables as loaded into WordPress.
- **Word files.** About 2,500 under `_CLIENTS/homedirections` and a similar number under an older backup folder, which may be the same files twice.

## Scope and timing, as Gordon set them the same night

This is Phase 2. It waits until the new system is built and has taken over from v3, and it runs on a dedicated thread. [gordon 2026-10-01] Within it: only the most recent Access backup matters; v1 is gone through although probably fine; v2 gets the close work; the Word files are audited as they are attached to client records. The inventory below is the starting list for that thread. Nothing further is done with it from the Phase 1 thread.

**mdbtools, installed 2026-10-01 on Gordon's say** (version 1.0.1 by Homebrew, which also installed its dependency unixodbc 2.3.14): it could **not** open the Access data files. `mdb-ver` reports "unable to open file" on all three copies of `Bkgdata.mdb` tried, though the files are readable. The first bytes of the newest file are not those of the Access 97-or-later format this tool reads, and the folder holds Access 2.0-era wizard files, so the data is most likely in the older Access 2.0 format. Unconfirmed. A reader for that format is a Phase 2 item. One lead for that thread: `EXPORT 20140722/booking_new07-22-14_*.sql` (July 2014) is, by its name, the booking data already exported to SQL.

## What an audit would do with these (a proposal, not started)

1. Open the Access data files read-only and count jobs by year. That needs a reader for the Access format on this Mac (none is installed; a new tool needs Gordon's say).
2. Load each database backup into a scratch database and count jobs and report notes by year in each. The differences between consecutive backups show what each event removed.
3. Build one table of every job ever seen in any source, with where it was seen, and compare it with the 9,442 rows in WordPress.
4. Only then decide what v4 migrates from where.
Client data stays on this Mac throughout; nothing is copied into a repository.
